# VDTP — 视觉数据传输协议

以**屏幕为发射器、摄像头为接收器**的离线数据传输。不使用互联网、Wi-Fi、蓝牙、NFC 或数据线。

发送端把文件编码成一串高密度黑白矩阵帧循环播放；接收端用摄像头连续拍摄、解码、重组，并用 SHA-256 校验。
信道是**单向**的——发送端不知道也不需要知道接收端状态，丢帧由喷泉码在文件级恢复，无需重传。

## 使用

### 发送端（Windows）

双击 `VDTP发送端.exe` → **把文件拖进窗口**（或点「选择文件…」）→ 选网格密度与帧率 → 「开始」。

「清空」把界面退回刚打开的样子：卸载文件、关闭会话、网格/帧率/调制深度都回到默认值。

播放窗口是**可拖动、可缩放的普通窗口**，把它拖到摄像头对准的那块显示器上。
`F11` 或双击全屏（用窗口当前所在的显示器，不是主显示器）；`T` 切换置顶。

先进入**握手阶段**：屏幕上是一个静止的元数据帧。让接收端读到它（接收端会显示出文件名和大小），
再按 `空格` 开始传输。`Esc` 或 `Q` 退出。

退出后再按「开始」会**接着原来的喷泉序列往下发**，不会从头重放：接收端会拒收已经收过的种子，
从 1 重来等于只给它重复帧，进度就卡在原地不动了。重新选文件或改参数才是新会话。

握手帧与数据帧密度相同，这是刻意的——如果握手帧更容易识别，你会在一个扛不住数据密度的
距离上按下开始。能读到握手帧，就说明当前距离和角度没问题。

x64 Windows 7 及以上直接运行，不需要 .NET、VC++ 运行库或任何依赖。

### 发送端（网页，跨平台备用）

打开 `sender.html` → **把文件拖到窗口任意位置**（或点选择框）→ 选参数 → 「开始播放」。
拖放在整页生效而不只是那个虚线框：文件落在没人接管的位置时浏览器的默认动作是**跳转过去打开它**，
页面就没了；所以 `dragover` 与 `drop` 一律拦下，只有拿它做什么才看当前状态。播放中拖入不会打断传输。

「清空」同样把页面退回初始状态。

### 接收端（Android，推荐）

安装 `VDTP接收端.apk`（需允许安装未知来源）→ 打开 → 授予摄像头权限 → 对准发送端屏幕。
识别完成后点"保存文件"，会弹出系统文件选择器让你决定存到哪里。

接收过程中和接收完成后都可以**回到起始页**重新开始：画面右上角的「返回起始页」、进度面板底部的
「停止接收并返回起始页」、完成面板的「返回起始页 · 再接收一个」，三个入口做的是同一件事——
关摄像头、丢掉解码器和全部计数、界面清空。会丢东西时会先问一句（已收到的编码块、还没保存的文件）。
不复用旧解码器是必须的：它会把下一位发送端的帧当成别人的会话拒收，进度还停在上一次的位置。

APK 里装的就是同一个 `receiver.html`（构建时校验逐字节一致），但它把页面挂在
一个 `https://` 源下提供，因此**绕开了下面那条限制**。Android 6.0 起可用。

### 接收端（网页）

用手机浏览器打开 `receiver.html` → 开启摄像头 → 对准发送端屏幕 → 自动识别并恢复文件。
三个「返回起始页」入口与上面的 APK 完全一致。

接收端优先选用**方形拍摄模式**（图案是方的，只有短边决定每模块像素数，16:9 把像素花在了用不上的那一轴），
拿不到方形模式时就用最大模式且不裁剪。帧率和分辨率都跟随相机原生能力：能否解码取决于每模块像素数，
任何降采样都是在扔掉决定成败的信息。定位时内部会按步长抽样（连通域搜索的开销与像素数成正比，
4K 全分辨率搜索每帧要几秒），但**每一个被解码的比特都取自原生像素**。

> **重要：`file://` 直接双击打开是拿不到摄像头的。**
> `getUserMedia` 要求安全上下文，Chromium 系不把 `file://` 算在内（WebView 同样如此）。
> 网页版必须通过 `https://` 或 `http://localhost` 访问：传到任意静态站
> （GitHub Pages 等）访问一次即可，之后完全离线可用；本机自测用 `npm run serve`。
> 不想折腾就直接用上面的 APK。

## 开发

```bash
npm test        # 全部测试
npm run build   # 构建全部交付物并校验体积预算
npm run serve   # 本地起 http://localhost:8080 供接收端使用（摄像头需要安全上下文）
```

构建产物会**剥离注释**。网页端内含完整解码逻辑，而 apk 里装的就是同一份页面
（`unzip -p VDTP接收端.apk assets/receiver.html` 即可读出），所以注释里的设计推理和
实测数据会随每一份拷贝一起分发。剥离减小体积约 38%，代码逻辑本身仍然可读——
这不是保密手段，只是不把设计笔记附送出去。

调试时想要可读产物：

```bash
VDTP_KEEP_COMMENTS=1 npm run build
```

剥离器是手写的状态机（正则做不对：`//` 会出现在字符串和模板字面量里）。
构建时会用同一组确定性运算对比剥离前后的行为指纹，**不一致直接构建失败**，
所以剥离出 bug 不会静默产出坏代码。

构建 Windows exe 需要交叉编译器：

```bash
sudo apt-get install gcc-mingw-w64-x86-64
```

构建 Android APK 需要：

```bash
sudo apt-get install default-jdk-headless android-sdk-build-tools \
                     apksigner zipalign android-sdk-platform-23
```

Debian 没有打包 dexer，`npm run build` 会自动从 Google Maven 拉取官方
`r8.jar`（纯 Java，与架构无关）缓存到 `build/out/`。
注意 apt 里的 `dx` 包是 OpenDX 可视化工具，**不是** Android dexer。

任一工具链缺失时 `npm run build` 仍会产出其余交付物，只是跳过对应产物并告警。

## 结构

```
core/     协议层（纯 JS，无依赖）  CRC32 / SHA-256 / PRNG / LT 喷泉码 / 帧格式 / 会话
visual/   视觉层                  矩阵编解码 / 定位与透视校正 / 网格锁定与帧间跟踪
native/   C 移植（仅发送端编码路径）+ 帧流状态机 + Win32 界面
android/  接收端外壳（WebView + 摄像头权限 + 保存桥接）
app/      两个网页应用的模板
build/    打包器、构建脚本、APK 构建、本地服务器
test/     测试（含 C 与 JS 的逐位一致性验证、APK 完整性校验）
```

数据通路：

```
文件 → 分块 → LT 喷泉编码 → VDTP 帧 → 黑白矩阵 → 屏幕
                                                    ↓ 光学信道
文件 ← SHA-256 校验 ← 重组 ← 喷泉解码 ← CRC32 ← 网格采样 ← 定位 ← 摄像头
```

### 条带与三级可靠性

一个矩阵横向切成若干**条带，每条带装一个完全独立的帧**。撕裂线上方的条带整条来自帧 N、
下方整条来自帧 N+1，**两边都是有效数据**——撕裂只毁掉跨越边界的那一条，不再是整帧作废。

实测（屏幕上 700px，1080p 拍摄）：128 网格 8 条带，撕裂下从 0 帧变成 7–8/8 条。
相对原来的整帧布局，有效交付 128 网格 6.8 倍、160 网格 11.2 倍。

条带数由代码按「撕裂下期望交付量」自选：64 网格 3 条、128 网格 5 条、256 网格 8 条。

握手帧例外，独占整个矩阵不分条带——它是静止的，撕不到它，而单条带也装不下元数据。

### 三级可靠性

- **模块级** Reed–Solomon（GF(256)，12% 冗余，跨块交织）：少量模块读错可以还原。
  实测把可用密度从 128 推到 192，同样帧率下单帧载荷从 393 B 提升到 3787 B。
- **帧级** CRC32：RS 也救不回来的帧直接丢弃，绝不返回猜测的数据。
- **文件级** LT 喷泉码：不要求收到任何特定帧，只要收到**足够数量**的独立编码块即可恢复。

因此摄像头丢帧、重复、乱序都不影响结果，也不需要任何反向信道。

## 已实测的工程约束

这些数字来自测试，不是估算：

| 约束 | 实测值 | 出处 |
|---|---|---|
| 每模块所需像素 | **≥ 4 px**（3.35 px 失败，4.15 px 成功） | `test/detect.test.js` |
| 定位判据 | 必须多候选逐个验证（显示器边框会冒充图案） | `test/monitor.test.js` |
| 二值化 | 必须局部对比度。全局阈值在暗房间下 89% 像素误判为暗 | `test/monitor.test.js` |
| 锁定后跟踪 | 5–26 ms/帧（40–180 fps），不再是吞吐瓶颈 | 实测 |
| 跨帧曝光 | 混合 35% 仍可解，50% 失败；**撕裂无论位置一律失败** | `test/monitor.test.js` |
| 自适应阈值 | 光照不均下 89/128 → 110/128 | `test/detect.test.js` |
| 发送端帧率 | 10 fps 在长曝光下仍有 79%；**20 fps 归零** | 实测 |
| 帧内纠错 | 160 网格 7/12 → 12/12；192 网格 6/12 → 10/12 | `core/ecc.js` |
| 喷泉码开销 | K=2048 最差 **1.17×**，K=512 最差 1.26×，K=40 为 1.90× | `test/lt.test.js` |
| 静区 | **必需**。无白边则无法定位 | `test/detect.test.js` |

这条是物理下限，不是可调参数。**默认 64×64**：128 要求图案在画面里占的面积约为
64 的两倍，手持拍显示器通常达不到（首次真机测试就卡在这里，一帧都没识别到）。

拍摄时让图案连同四周白边尽量占满画面。接收端的诊断读数会直接告诉你差多少：

- **定位候选 = 0** → 连暗色外框都没找到，光照或对比度问题
- **结构误差 > 20%** → 找到了但不是本协议的帧（多半锁到了显示器边框），或者太糊
- **每模块像素 < 4** → 拍得太远，靠近或降低网格密度

各网格单帧容量：

| 网格 | 载荷 | 10 FPS 理论吞吐 |
|---|---|---|
| 64 × 64 | 393 B | 3.8 KB/s |
| 128 × 128 | 1833 B | 17.9 KB/s |
| 256 × 256 | 7785 B | 76.0 KB/s |
| 512 × 512 | 31977 B | 312 KB/s |

## 当前未实现

按 V2.0 路线图，以下属于后续阶段，现在**没有**：

- 压缩（Zstd/Deflate）与加密（AES-256-GCM / X25519）——元数据里已预留 `compression`/`encryption` 字段，当前恒为 `none`
- 帧内 Reed–Solomon / BCH 轻量纠错（`ecc` 字段恒为 0，当前只有 CRC32 丢弃策略）
- 自适应码率（按信道质量动态调整密度/帧率/ECC）
- 彩色与多级灰度调制
- RaptorQ（当前为 LT，开销 22% 对 RaptorQ 约 2%）

## 移植须知

`core/prng.js`、`core/lt.js` 与 `native/vdtp.c` 构成**线路契约**。帧里只带一个 32 位种子，
两端各自从它重新生成邻居集——任何移植必须逐位复现 `mix32`、xorshift32 与量化后的
soliton 分布表，否则解码端会 XOR 错块，产出的文件直到最后 SHA-256 才暴露损坏。

`test/parity.test.js` 通过比对完整 CDF 表与 15000 组邻居集，逐字节证明 C 与 JS 一致。
新增移植时请扩展该测试。
